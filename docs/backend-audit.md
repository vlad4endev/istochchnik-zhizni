## Находки

### Высокий приоритет

1. **RLS не включён у таблиц, которые создаёт код.** После старта API по коду: 70 таблиц, RLS у 0.
   RLS включали отдельной миграцией один раз (`20260408120000_enable_rls_public_tables`) для таблиц,
   что существовали на тот момент, и в `profile_system`. Всё, что `initDb`/`ensure*Schema` создали позже,
   в облаке может остаться без RLS. Если у Supabase включён Data API и у ролей `anon`/`authenticated`
   есть права на `public`, такие таблицы читаются с публичным ключом, минуя API.
   **Нужно проверить в облаке** (разделы 3–5 скрипта). Исправление: идемпотентный шаг, который включает RLS
   на всех таблицах `public` и отзывает права у `anon`/`authenticated` — после каждого создания таблиц.

2. **API при каждом старте выполняет DDL и сид на облачной БД.** `initDb()` гоняет весь `INIT_SQL`
   (69 `CREATE TABLE IF NOT EXISTS` и `ALTER`) и `MEMBER_SEED_SQL`, если не задано `SKIP_DB_INIT_ON_START=true`.
   Документация (`docs/operations.md`) требует `true` для Supabase, но в `docker-compose.prod.yml` и
   `docker-compose.yml` по умолчанию `false`. Забыли переменную — схема меняется на боевой базе при рестарте.
   Исправление: по умолчанию `true` для прод-компоузов, а запуск DDL — отдельной явной командой.

3. **TLS к БД не проверяется.** `DB_SSL_REJECT_UNAUTHORIZED` по умолчанию `false`, и в документации он так и
   рекомендован. Соединение шифруется, но сертификат сервера не сверяется — возможна подмена в сети.
   Исправление: взять CA-сертификат Supabase и включить `DB_SSL_REJECT_UNAUTHORIZED=true`.

### Средний приоритет

4. **Повтор любого запроса после обрыва.** `query()` в `src/config/db.ts` при `ECONNRESET`/«Connection terminated»
   повторяет запрос целиком. Для `INSERT`/`UPDATE` это может продублировать запись, если соединение
   оборвалось уже после выполнения. Исправление: повторять только чтение.

5. **Три источника схемы, миграции не собирают пустую БД.** `initDb.ts`, ~30 `ensure*Schema` и
   `supabase/migrations` (118 файлов) расходятся; `docs/db-schema.md` фиксирует 16 падающих миграций и
   разницу в 196 колонок. Воспроизводимой схемы и надёжного пути восстановления «с нуля» нет.
   Сверка: `scripts/schema-drift.sh`.

6. **Шифрование сообщений.** `src/lib/messageCrypto.ts`: AES-256-CBC без аутентификации (нет MAC/GCM —
   шифртекст можно подменить незаметно). Если `MESSAGE_ENCRYPTION_KEY` пуст или неверен, сообщения
   **молча сохраняются открытым текстом**. Потеря ключа = потеря прочтения истории.
   Исправление: в production падать при отсутствии ключа, перейти на GCM с версионным префиксом
   (старые записи читать по-старому), хранить копию ключа отдельно от базы.

7. **`DELETE /api/calendar/events` удаляет все события** одним запросом, защита — только роль администратора.
   Исправление: требовать явное подтверждение в теле запроса.

### Низкий приоритет

8. В корне лежит `fix_db.ts` — разовый скрипт с `rejectUnauthorized: false` вшитым в код. Удалить или перенести в `scripts/`.
9. Заголовок `X-Powered-By: Express` отдаётся наружу (`app.disable('x-powered-by')`).
10. В миграциях Supabase лежат реальные имена и телефоны (сиды участников, `set_chendev_vlad_admin_and_phone`):
    это персональные данные в репозитории и его истории.
11. Автобекап выключен (`[CRON] backup: автобекап выключен`). Проверьте, что резервные копии облака
    делаются и что восстановление пробовали.

## Как проверить облако

Скрипт только на чтение: сессия переводится в read-only, запись отклоняется (проверено).

```bash
# лучше с отдельной ролью, которой выдан только SELECT:
AUDIT_DATABASE_URL='postgresql://аудит:***@хост:5432/postgres?sslmode=require' bash scripts/db-audit.sh
```

Он покажет: роль и TLS соединения, сводку и список таблиц без RLS, права `anon`/`authenticated`,
таблицы без первичного ключа, журнал миграций, размеры, число соединений, расширения, дубли участников,
просроченные сессии, долю зашифрованных сообщений.

Минимальная роль для аудита (выполняется владельцем облачной базы в SQL-редакторе):

```sql
CREATE ROLE db_audit LOGIN PASSWORD '<длинный случайный пароль>';
GRANT CONNECT ON DATABASE postgres TO db_audit;
GRANT USAGE ON SCHEMA public TO db_audit;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO db_audit;
-- после аудита: DROP OWNED BY db_audit; DROP ROLE db_audit;
```

Результат можно прислать сюда, пароль в чат не нужен.
